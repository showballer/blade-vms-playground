# app(3) 转盘对接与 5 秒一圈换点评估

更新日期：2026-10-20。

## 业务范围

叶片离开当前点位 → 停止当前点位的数据接收并保存 → 两轴定位到下一个点位 → 确认停稳 → 恢复采集并等待叶片进入、离开。

本次不实现连续追踪，也不假设每次换点都能赶上同一圈。转盘移动期间不做叶片进入/离开判定；激光保持原来的常亮策略。已有本机记录、有效时间窗、上传格式不变。

界面入口：**转盘点位 → 标题旁“转盘状态”**。先重新检查，按故障类型处理。每次恢复都会重新读取设备；旧状态、零速、命令已应答均不能替代恢复成功读回。

待启动轨迹先点“取消待执行轨迹”；已结束或故障的旧轨迹使用“清除旧轨迹”。取消后固件正常返回“已取消（8）/人工停止（1）”，不要求再清一次才能开始。控制器断电重启会自行丢失RAM预载和参考有效性，客户端保存的作业原点坐标保留，但必须重新核验真实参考，不能在任意位置强设零。

### 断电后的参考恢复

用户已确认 app(3) 实际操作结果为先显示 +25°，再走到0°，与收到的源码一致。

1. 在**转盘点位 → 手动控制**选择俯仰轴、读取反馈。仅在实体确实处于厂家规定的 +25°传感器参考姿态时，点击“确认当前为+25°参考”。任意机械限位并不都代表这个角度。
2. 确认读回 +25°、无故障并启用保护后，点击“俯仰回水平0°”。此时才执行运动；速度采用上方当前轴的“定位转速”。
3. 水平轴则在现场确认的零姿态点击“确认当前为0°参考”；不要把俯仰轴也直接当作0°设定。
4. 顶部“设置归零 / 回到原点”仍是公共光学作业坐标，与设备水平0°分开。重新建立硬件参考后，历史点位与作业原点仍按参考签名重新核验，不自动把旧坐标绑定到新参考。

旧服务将参考恢复与软限位配置共用同一检查，导致“反馈故障3 / 参考失效”也无法进入恢复。现拆开检查，仅显式参考恢复允许这一特定情形；所有采集、换点、回原点和软限位配置继续使用原运动保护。恢复请求不会启动采集或自动走到0°。

若同时留有本端口、本轴的停止未确认记录，只有SDK停止、参考恢复和最终停稳读回均通过，才解除该轴的停止记录；另一轴仍待确认时保留其警告。其他串口的警告、活动轨迹或恢复失败均不能通过重新标定抹除。

Mac 与 Windows 使用相同共享界面、Electron 桥接和 Python 协议代码。已有 Windows 安装包中的冻结服务不会随本地源代码自动更新；需要后续重新构建、打包才能包含这些改动。

来源：本机 `../app(3)/README.md`、`motor_controller.py`、`protocol.py`、`trajectory.py`、`faults.py` 和附带测试。README 引用的 `../docs/` 文档没有包含在本次收到的目录中。未替换整个厂商驱动，保留了平台的 Mac 串口、停止确认、参考位核验和禁止未知结果重发逻辑。

## app(3) 速度差异逐项复核

用户确认同事使用“两轴轨迹试验”及 rpm 设置。源码中主窗口 `speed_rpm` 只用于单轴定角，轨迹窗口单独使用 `values['speed']`（°/s），两者没有联动；主窗口的rpm数字不能作为双轴实际下发速度的证据。

| 项目 | app(3) | 平台本次处理 |
| --- | --- | --- |
| 单轴速度换算与运动帧 | 减速比50:1、0.01rpm分辨率 | 保持一致；对0.02/0.25/0.6/1/3/5/10rpm共42组单轴及轨迹头数据做离线逐字节对比，一致，无真实I/O |
| 共同减速 | 轨迹编辑窗口默认开启 | 原先未启用，本次统一接入，不移除跟随保护 |
| 控制周期 | 轨迹编辑默认100ms；一键小幅调试预设250ms | 原先250ms，本次轨迹执行及短距离轨迹采样改100ms，兼容性由实际预载应答核验 |
| 等待时间 | 默认计划×4+35秒 | 原先服务计划+15秒、SDK固定30秒，本次对齐共同减速等待；显式SDK超时仍保留调用者设置 |
| 速度设定含义 | 自有轨迹路径与时长；max_speed为上限 | 平台还按叶轮周期、点位间隔和行程计算上限，再按起停加速度生成三次平滑路线；填10rpm不保证短行程达到10rpm，现显示本段实际下发上限 |
| 终点容差 | 日常预设0.3° | 保留平台原有0.1°到位标准，因此收敛等待可能更长；不能只放宽控制器容差而跳过最终实测位置核验 |
| 驱动加减速 | 主窗口可单独临时设置PA40/41/42；业务轨迹API不写这三个参数 | 新增只读诊断，未自动写成SDK默认值。能否匹配同事现场效果，还需对比其真实读值与同一条轨迹 |

共同减速属于向控制板发出的运动策略，预载应答只说明参数被接受，不代替固件行为、实际速度、位置误差及叶片有效采集的实机验收。当前源码缺少控制板固件版本查询；不凭0x30支持就宣称已验证共同减速的物理效果。

### 跟随误差与回原点故障

后续用户报告回原点时俯仰误差0.774°、水平0.013°，超过原先固定0.75°。本轮读取服务保存的最后反馈，轨迹为故障7、两轴零速且参考有效；当时USB与网线已拔出，因此这些是最后保存的反馈，不能当作重新连接后的实读结果。

0.75°不是终点到位精度。app(3)轨迹面板也默认0.75°，其低层通用API默认5°；对应协议只接受0.5～10°，没有禁用值。本次将平台的固定值改为明确配置，保留默认值和有限保护，未自动增大用户设置。提高误差上限不证明设备已能跟上，也不能代替对速度、加速度、负载及实际误差的验证。

失败后控制器会锁存故障轨迹，新的回原点会被拒绝，不表示作业原点丢失。原点区域现提供独立清除入口：只对重新读取并匹配的会话发送清除，后台和SDK均核对会话；清除后核验两轴停止、原参考及保护不变。不会重新设零、自动续采或重发失败运动。

## 纯运动时间计算

使用平台实际 `station_move_plan()`，双轴同时移动，以较大轴的角度变化为准，包含起停加速度和指令量化，不含通信、数据保存、SDK关闭/启动与停稳回读。

起停三次平滑轨迹的初始时间：

`T = 1.05 × max(1 s, 1.5 × Δθ / (6 × rpm), sqrt(6 × Δθ / acceleration))`

随后按毫秒、毫度量化，并逐段校核速度/加速度，必要时增加时间。最短上传轨迹仍为1 s，因此平台最短规划值为1.05 s。

| 测点 | 距旋转中心 | 最大单轴换点角 | 5 rpm / 3°/s² | 3 rpm / 30°/s² | 3 rpm / 60°/s² | 4 rpm / 90°/s² |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P1 | 0.078 m | 1.354° | 1.728 s | 1.050 s | 1.050 s | 1.050 s |
| P2 | 0.234 m | 4.056° | 2.991 s | 1.050 s | 1.050 s | 1.050 s |
| P3 | 0.390 m | 6.740° | 3.856 s | 1.220 s | 1.050 s | 1.050 s |
| P4 | 0.546 m | 9.395° | 4.552 s | 1.440 s | 1.050 s | 1.050 s |
| P5 | 0.702 m | 12.009° | 5.146 s | 1.628 s | 1.151 s | 1.050 s |

这些是软件计算值，**不是实机达到的速度、允许的机械参数或验收结论**。厂商本次 README 的保守初调建议仍为0.5～1.5°/s和1～3°/s²，等价输出轴约0.083～0.25 rpm；高于此区间须验证实际负载和跟随误差。协议允许的最大值不等于设备已经验证的工作参数。

## 对“赶到下一个点位等待”的结论

1. 按跨圈等待方式，5秒一圈不要求整条采集路线也在5秒结束。先保证停稳和捕获有效经过，允许错过本次后等下次；等待超时仍明确报错，不把缺失点记成采集成功。
2. 如果要求当前圈下一90°点位就采到，所有交接步骤必须在约1.25秒内完成（还应扣除当前叶片离开判定与光斑覆盖时间）。即便3 rpm/60°/s²，最外点纯运动就用掉1.151秒，只剩不到0.10秒；4 rpm/90°/s²也只剩约0.20秒。当前逐点保存、上传轨迹及DAQ重启不具备这样的端到端时延证明。
3. 因此不把10 rpm/120°/s²作为推荐设置。达到1.05秒下限后继续提高几乎无收益。3 rpm/30°/s²可作为后续逐步提高时的计算比较点；3 rpm/60°/s²作为更快的实验比较点，均须实机逐项验证，不自动写入用户配置。
4. 页面每圈时间改5、最长等待保持2圈（10秒）可用于跨圈测试；确认进入且离开后才换点。等待时间从新点采集就绪后计算，不代表保证接到同一圈。
5. RSSI只识别有叶片经过，不能区分3个叶片的身份。缺少位置基准/标记识别时，界面的叶片编号是用户归档标签，不能证明每个有效片段来自同一片实物叶片。需要严格同叶片归属时还须补位置基准或识别验证。

实机验收应记录：离开确认、记录接收停止、运动命令、实际双轴停稳、DAQ就绪、下一次进入/离开；用完整交接时间判断赶上哪次经过。不得仅用UI规划时间或下位机接受命令判断通过。
