# 连续采集与自动换点测试说明

改造前基线为 Git 标签 `v1.0`，对应 `dbfe3706cacba80e90989ad0103735ccd14dc551`。
标签用于回溯源码，不改变安装包显示的版本号。本次修改共用的 Python 采集服务，适用于 Mac 和 Windows；没有修改控制板固件或转速、到位误差、叶片判定阈值。

## 本次行为

| 环节 | 新行为 |
|---|---|
| 开始任务 | 建立一次 DAQ 采集，检查本机 SDK 支持非阻塞缓存读取，再开始定位 |
| 等待叶片 | 到位后确认数据格式，排空旧缓存，重新建立背景并判断完整进入和离开 |
| 叶片离开 | 接收线程立即冻结当前点位的判断和数据边界，唤醒换点线程 |
| 转盘移动 | DAQ 持续接收并保存全量原始数据；禁止移动中的叶片信号触发下一次换点 |
| 下一点到位 | 使用本次操作的新鲜双轴反馈，过期或不完整时重新读取；开新的点位数据窗口 |
| 数据保存 | 有界后台队列写盘，换点不等待上一点的文件收尾；文件确实写完后才计为已保存 |
| 故障或停止 | 关闭点位判定，停止采集并保留已收到的数据；队列满、磁盘错误、采样格式变化均报错，不忽略错误继续运行 |

复用的反馈最多有效 0.5 秒，仅限同一次控制连接。两轴参考、报警、目标范围和最终到位条件仍需通过。激光仍遵循原有任务策略：正常换点保持开启，异常或取消进行原有关闭处理。

## 源码更新后启动

先退出旧客户端，拉取 `main`。必须重启采集服务，单独刷新页面不会加载新的 Python 逻辑。

- **Mac**：使用现有 `services/acquisition/.venv`，重新启动源码客户端即可；重新构建桌面页面可执行 `npm run build -w @blade/desktop`，然后 `npm run desktop`。
- **Windows**：客户端默认启动打包的 `BladeAcquisition.exe`，只执行 `git pull` 不会更新已有 EXE。需要在 Windows 重新构建完整采集服务目录，再启动桌面端。示例（路径替换成同事机器上的实际路径）：

```powershell
.\services\acquisition\build-windows.ps1 -Python "C:\Python312\python.exe" -SdkDirectory "C:\VendorSDK\x64" -SdkLicenseDirectory "C:\VendorSDK\licenses" -StageDesktop
npm run build -w @blade/desktop
npm run desktop
```

设备与服务若配置过自定义 EXE 路径，应切换到本次构建的服务。完整依赖目录必须与 EXE 一起使用。出现“不支持连续采集缓存边界确认”时，更新本机 Polytec SDK；程序会在首次定位前拒绝本次连续任务。

## 同事实测步骤

保持上次两点、转速和 RSSI 参数，先只比较软件改造的影响。

重开客户端后的“作业原点已保存·待核验”不会清空路线或禁用操作。点击预定位或开始采集时，必要时读取一次当前双轴参考；参考一致才沿用原点坐标，参考变化或读取失败会显示错误并阻止运动。没有角度缓存也可以发起核验。按钮不能使用时，测点行直接显示具体原因；预定位只需要转盘连接和本机服务，不要求配置测振仪 SDK。顶部激光显示“未知”本身不会锁住预定位；真实采集仍须通过设备端的激光状态读回。

| 步骤 | 操作 | 检查结果 |
|---|---|---|
| 1 | 核对两轴参考、作业原点及两点坐标；保持原先的安全运动范围 | 当前反馈正常，两个点确实有叶片经过 |
| 2 | 在数据采集选择原先的两点联动路线，可先“移动到预设位置” | 已在首点时开始采集不重复移动 |
| 3 | 开始采集，让风机保持约 5 秒一圈，连续测几个往返 | 每个点在背景就绪后识别一次完整经过；离开后只触发一次移动 |
| 4 | 观察换点期间其他叶片扫过光束 | 不应再次触发换点或跳过下一个点 |
| 5 | 正常结束，等待保存完成 | 点位记录齐全；可以打开波形、导出和上传 |
| 6 | 另开一个短任务，在等待叶片时停止 | 不再移动；部分记录保留，未完成记录不冒充完整记录 |

优先比较记录内 `pointCycle.handoff` 的 `detectedAt → motionCommandAt → arrivedAt`，以及下一记录的 `firstSampleAt` 和背景就绪事件。连续模式使用 `detectorGatedAt`，不再用旧的 `receiverPausedAt` 表示换点边界。主机时间是观测时间，不是硬件同步时间戳。

## 本机数据位置与兼容

数据目录由桌面端“打开数据目录”访问：

```text
field-data/
  recordings/<点位记录ID>/          # 原有格式；仅当前点静止等待/叶片经过的数据
  continuous-sessions/<全量记录ID>/ # 本次任务连续原始数据，包含首次定位和换点过程
```

点位 manifest 的 `pointCycle.continuousSession` 保存对应全量记录 ID、相对目录和原始全局样本范围；`bufferFence` 记录到位后的 SDK 缓存边界。两者标注 `sampleClock=continuous_session_raw`，上传降采样不会把全局索引误改成局部索引。

现有波形、有效段分析、任务 ZIP 和 Web 上传继续使用点位记录。全量移动段留在本机，当前不额外加入任务 ZIP 或上传。诊断全量数据时可复制对应 `continuous-sessions/<ID>` 目录；它使用相同的 BLADEV01 分块格式，可用现有 `export_csv.py` 转换。

同时保留全量任务流和点位记录会增加磁盘占用；点位数据是全量流的一个子集。正常结束会等后台保存完成；若磁盘持续过慢，程序报错停止，不无限堆积内存。后台线程未退出前禁止启动新任务。

## 本次离线验证

- 真实 SDK 接口的 Mac／Windows 内存替身验证一次 DAQ 跨点、移动数据隔离、取消、格式变化和迟发磁盘错误；没有连接真实设备。
- 昨晚 24 条记录共 5,245,000 个样本回放，96 个进入/确认/离开/触发索引与原记录一致；再将相同波形作为移动段输入，24 次经过均未触发点位判断。55 个原始文件读前后哈希一致。
- 本机临时磁盘 250 kHz 双副本压测，每份 1,250,000 样本完整保存；该结果不代表同事的 Windows 硬盘和 SDK 性能。

这次结果证明离线逻辑和保存路径成立。真实指令延迟、停稳时间，以及是否赶上下一片叶片，需用更新后的客户端重新记录和比较；不能用离线耗时代替实测。
